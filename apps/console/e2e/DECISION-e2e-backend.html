Testing Against Production

We want the end-to-end test suite to run on every pull request. Doing that against the production backend would require opening production to a new browser origin — and the only way to do it cheaply is not safe. This memo lays out what we found and asks for four decisions.

Repository openlane-ui Branch feat-playwright-e2e Status awaiting decision

The ask

What we need you to decide

  1. Which option we build. Three are on the table. One costs $100/month, one is free but serialises pull requests, one changes nothing on production at all.
  2. Whether CI may create and delete organizations on production. Required for the production options. A single permanent test organization degrades the suite over time — we have measured this.
  3. Whether four permanent test accounts may exist on production. One per role, and who holds the credentials.
  4. Whether losing ~45 tests is acceptable. Including all onboarding coverage, which our own priority list marks as Tier 0, in exchange for five gained. This is the argument that we think should decide it.

Context

Where things stand

The suite is 723 tests across 36 files. A full local run is currently 714 passed, 0 failed, 3 flaky, 6 skipped in 9.8 minutes. CI is built and ready: four parallel shards on every pull request, each bringing up its own throwaway backend from the published theopenlane/core image, plus a job that merges the four reports into one. Local commits never run E2E, so day-to-day work is unaffected.

The open question is where the backend comes from. Today each shard runs a disposable one. The alternative is to point the tests at the production backend, using the Vercel preview deployment that every pull request already gets. That would test the real build against real data.

One correction to a figure that circulated earlier in this discussion: the trust centre is not untested. All eleven trust-centre tests pass on a developer machine, verified in a fresh run — the local seed data includes an organization with a trust centre configured. Seven of them assert the error page that an organization without a trust centre should see, and need no seed at all. Only four depend on that seeded organization, so the throwaway backend in CI would skip four tests, not the twelve quoted before.

Finding

The cheap version of this is not safe

The browser calls the API directly, so production would have to list the preview deployment's origin in its CORS allow-list. Preview URLs look like openlane-ui-git-<branch>-openlane.vercel.app and change with every branch, so the obvious move is a wildcard such as https://*openlane.vercel.app.

That does not work the way it looks. The API compiles allow-list entries into anchored regular expressions, turning * into .*: 

pattern := regexp.QuoteMeta(origin)
pattern = strings.ReplaceAll(pattern, "\\*", ".*")
pattern = "^" + pattern + "$"

// https://*openlane.vercel.app
//   compiles to  ^https://.*openlane\.vercel\.app$
//   which matches  evil-openlane.vercel.app

Why this is exploitable

vercel.app is on the Public Suffix List precisely because its subdomains are user-controlled and mutually untrusted. Anyone can register a Vercel team whose slug ends in openlane and deploy to a hostname that satisfies the pattern. Credentials stay enabled for wildcard patterns — they are only disabled for a literal *.

The result: a page controlled by someone else, visited by any logged-in Openlane user, could make authenticated requests to the production API as that user and read the responses. CSRF protection does not help, because an allowed origin can request a CSRF token for itself.

Narrowing the pattern does not fix it — *-openlane.vercel.app is satisfied by a team slug of anything-openlane. No wildcard over vercel.app is safe. Whatever we do, it has to be on a domain we control.

The choice

Three options

A · Vercel Preview Deployment Suffix

$100 / month

A paid Vercel feature that puts every preview deployment on our own domain, so the CORS entry becomes https://*.preview.theopenlane.io — a wildcard, but only over hostnames we control. Pull requests keep running in parallel.

Cost
$100 per month, ongoing
Prod CORS
Wildcard over our own domain
Parallel PRs
Yes

B · One fixed alias

free

Add a single subdomain to the Vercel project, and have CI point it at the pull request's deployment just before the tests run. Production then allows exactly one origin — no wildcard, no pattern matching, the tightest possible change: 

vercel alias set <deployment-url> e2e.preview.theopenlane.io

# production CORS
alloworigins:
  - https://e2e.preview.theopenlane.io

The alias is global, so only one pull request can be tested at a time. GitHub keeps one run going and one waiting; a third displaces the one that was waiting, so during busy periods some pull requests need their run started again by hand.

Cost
None
Prod CORS
One exact origin — narrower than option A
Parallel PRs
No, one at a time

C · Keep the throwaway backend

built and working

What we have now. Every shard starts its own backend, runs its quarter of the suite and throws it away. Production is never involved, so none of the questions in this memo apply. The one thing it cannot check is the Vercel build artefact itself — the same code, built by CI instead of by Vercel.

The arithmetic

Production costs us more tests than it gains

Production runs with developer mode off, as it should. Our setup creates a fresh set of users for every run by registering them through the API and reading back the verification token — something the backend only returns in developer mode. Against production that is impossible, so every test that needs a brand-new user cannot run.

CoverageAgainst productionTests
Onboarding — the entire file, Tier 0 in our own priority listCannot run17
Fresh-organization blocks across nine filesCannot run18
Sign-up and email verificationCannot run~10
Trust centre — only the tests needing a seeded organizationGained+5

Net, moving to production loses roughly 40 tests and gains five. And those five have a cheaper fix that works everywhere: the backend already exposes a createTrustCenter mutation with no required fields, so the suite can create its own trust centre instead of relying on seed data that happens to be present on the machine running it. That closes the gap under option C too, at no cost and with no production changes.

If we go to production anyway

What options A and B would require

  • A fresh organization for every run, not one permanent one. We measured this on a shared organization that had accumulated months of test data: three tests passed in 14 seconds against a fresh organization, while twenty failed against the reused one. Records pile up, list pages slow down, tests start failing for reasons unrelated to the code. Both the create and delete operations exist in the API, so each run can clean up after itself.
  • Four permanent accounts, one per role. Our largest spec file is 59 tests checking what each role may and may not do, and 30 further places switch role mid-suite. Without developer mode we cannot create those users per run, so they have to exist permanently and be added to each run's fresh organization.
  • Credentials as repository secrets. Pull requests from forks do not receive secrets, so E2E would not run on outside contributions.
  • Destructive operations against production. The suite creates and deletes records, including bulk deletes. Contained to the run's own organization, but happening on production.
  • Real invitation emails. The user-management tests send invitations, which on production means real email delivery.

Recommendation

Stay on the throwaway backend, and seed the trust centre ourselves

Option C is already built and green. Adding a createTrustCenter seeder closes the only gap production was going to fill — all five tests of it — costs nothing, changes nothing on production, and removes the suite's one dependency on seed data that has to already exist on the machine running it.

If verification against the real backend is still wanted afterwards, we would add it as option B on a schedule — once a day on main, serialised, running only the tests that do not need user registration. At that cadence the serialisation and the missing 45 tests stop mattering, because the full suite still runs on every pull request under option C.

We would only recommend paying for option A if previews on our own domain are wanted for reasons beyond testing.
